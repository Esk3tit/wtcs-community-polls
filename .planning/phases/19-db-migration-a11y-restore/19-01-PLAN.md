<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated client → Postgres (via PostgREST) | Authenticated supabase-js .from('profiles').update() calls pass through RLS then hit the BEFORE-UPDATE trigger |
| SECURITY DEFINER RPC → Postgres | update_profile_after_auth executes as the function owner; sets GUC before issuing UPDATE |
| PgBouncer pool → next transaction | Transaction-local GUC must not survive connection return to pool |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-01 | Elevation of Privilege | profiles table / profile_self_update_allowed trigger | mitigate | Migration 15 replaces the permanently-false current_user = session_user gate with GUC check — direct client UPDATE to is_admin/mfa_verified/guild_member is now rejected when app.trusted_profile_update is absent |
| T-19-02 | Spoofing | app.trusted_profile_update GUC — can a client set it directly? | mitigate | PostgREST does not expose SET commands or set_config() to unprivileged clients. The GUC is set only inside update_profile_after_auth (SECURITY DEFINER), which executes as the function owner. An unprivileged authenticated-role client cannot call set_config via PostgREST SQL because PostgREST uses the authenticated role context, not the owner role. The only path to set the GUC is through the SECURITY DEFINER RPC, which is the intended trusted path. |
| T-19-03 | Elevation of Privilege | PgBouncer connection pool — GUC leakage across transactions | mitigate | set_config('app.trusted_profile_update', 'on', true) uses is_local=true (third argument), scoping the GUC to the current transaction. PgBouncer transaction-pooling mode returns the connection after each transaction. A transaction-local GUC is cleared at transaction end — it cannot persist to the next user's transaction on the same pooled connection. Session-local (is_local=false) was explicitly rejected in D-01. |
| T-19-04 | Tampering | profile_self_update_allowed — dead-code risk on protected-column branch | mitigate | D-05 mandates a regression test (profile-trigger-gate.test.ts) that proves the protected-column branch fires on direct client UPDATE. Without this test, the branch would remain as suspected-dead code. The test turns it into a proven security control. |
| T-19-05 | Tampering | Migration 15 — DROP + CREATE would sever trigger OID binding | mitigate | PATTERNS.md and RESEARCH.md both flag this: always CREATE OR REPLACE FUNCTION; never DROP + CREATE. The trigger on_profile_self_update references profile_self_update_allowed by OID — DROP changes the OID and silently disables the trigger guard. The migration uses CREATE OR REPLACE exclusively. |
</threat_model>
