<objective>
Bump the Supabase CLI pin from `2.92.1`/`2.98.2` to ONE resolved stable release that bundles `supabase/edge-runtime:v1.74.0`, and apply that SAME version to all four pin locations so local and CI run identical runtimes — fixing the ES256 JWT-verification bug AND closing the local/CI version-skew gap (REVIEWS HIGH-1).

Purpose: CLI v2.92.1 bundles `supabase/edge-runtime:v1.73.3` which has the ES256 fallback-to-HS256 bug described in `supabase/config.toml` lines 24–30. The edge-runtime v1.74.0 (released 2026-04-30) fixes this. Since the edge-runtime image version is bundled per CLI release (no independent pin mechanism), the fix is to advance the CLI version.

REVIEWS HIGH-1 (Codex HIGH + Cursor HIGH, verified): the repo today has FOUR divergent pins — `package.json` `"supabase": "2.98.2"`, `ci.yml` `test-integration` `2.92.1`, `ci.yml` `e2e` `2.92.1`, and `deploy-edge-functions.yml` `2.92.1`. The original plan only edited `ci.yml`, so `npm run test:integration` would validate against the local `2.98.2` stack while CI ran the bumped pin — the local-green claim would NOT prove the CI pin works (violates L-03 "green locally AND in CI" and D-04 exact-pin). The fix is to resolve ONE semver and apply it to all four locations, then prove the local stack actually runs that version before trusting the local suite.

The executor MUST resolve the exact latest STABLE CLI semver at execution time from `https://github.com/supabase/cli/releases` — do not use a guessed literal, and explicitly skip `-beta`/`-rc`/prerelease tags (Codex/Cursor MEDIUM: stable listings showed `v2.102.0` stable alongside `v2.103.0-beta.*` prereleases). Prefer the smallest verified version that bundles edge-runtime >= v1.74.0 if the very latest stable regresses.

Output: One resolved stable version applied to all four pins (ci.yml ×2 + deploy-edge-functions.yml + package.json/package-lock.json), a recorded `supabase --version` parity check proving the local stack matches, and the full integration suite green locally and in CI.
</objective>
