<objective>
Write Migration 15 (`00000000000015_trusted_profile_update_guc.sql`) that replaces the broken `current_user = session_user` gate in `profile_self_update_allowed` with a transaction-local GUC flag set by `update_profile_after_auth`, closing the privilege-escalation path where direct client UPDATEs to `mfa_verified`, `is_admin`, and `guild_member` were silently accepted.

Also create the integration test `profile-trigger-gate.test.ts` that proves both gate directions work and that the proof is meaningful: direct client UPDATE to each protected column (`mfa_verified`, `is_admin`, `guild_member`) is rejected, an allowed-column UPDATE (`discord_username`) still succeeds, and the RPC path is verified with an **ordered flip-then-call-then-read-back** assertion (so a no-op write cannot pass) plus a post-RPC direct-update rejection that proves the transaction-local GUC did not leak across requests.

This migration also makes the `update_profile_after_auth` EXECUTE grant explicit and documents its trust boundary in a `COMMENT ON FUNCTION`. Per the review, closing the direct-PostgREST escalation shifts the entire trust boundary onto this RPC; the RPC trusts caller-supplied `p_mfa_verified` / `p_guild_member` (computed client-side in `src/lib/auth-helpers.ts`) and updates only the caller's own row (`auth.uid()`). Server-side re-derivation of Discord MFA/guild state is **out of scope** (pre-existing OAuth-callback design, no live users) and is recorded as an accepted residual in the threat model.

The migration file and test file are created in this plan (Wave 1). The test will be RED (failing) until `supabase db push` runs in Plan 03 (Wave 2). That is expected — the file must exist and be syntactically correct before the push.
